# 4.0.1 Performance & Reliability Hardening

This document records the renderer, cache, test, and benchmark hardening shipped with 4.0.1 and the follow-up fixes applied on the hardening branch.

## Blur lifecycle and concurrency

`BlurMaker` is shared process-wide through `NeuBlurMakerHolder`.

The mutable graphics state is protected by one lock so concurrent blur requests cannot race through the RenderScript backend or the reusable bitmap pool.

On API < 31, the implementation may use the legacy RenderScript backend. On API 31+, the implementation uses the StackBlur path and does not keep a persistent RenderScript context.

A RenderScript runtime failure is treated as transient: resources are reset and the same request falls back to StackBlur instead of permanently poisoning the shared singleton.

## Shadow cache

`NeuShadowCache` is an LRU cache measured in bitmap kilobytes.

The key includes:

- render pass
- pixel dimensions
- exact IEEE-754 elevation bits
- exact IEEE-754 stroke-width bits
- blur-downsampling configuration
- light/dark colors
- corner descriptor
- light-source direction

Using exact float identity avoids approximate-bucket collisions between render parameters.

The cache also responds to `ComponentCallbacks2` memory-pressure notifications. Severe pressure evicts the cache; lower pressure temporarily reduces the active budget. The normal configured budget is no longer restored implicitly by each `NeuBlurMakerHolder.get()` call, because doing that could immediately undo a memory-pressure trim while a screen is being recomposed. Apps can explicitly restore a larger budget through `NeuPerformanceConfig.shadowCacheBudgetKB` when appropriate.

`NeuPerformanceConfig` values are `@Volatile`, so configuration writes and reads have defined visibility across the renderer's threads.

## Shadow generation allocations

Compose shadow draw paths compute the cache key before constructing `GradientDrawable` instances. Cache hits therefore avoid those drawable allocations entirely.

Blur source dimensions use ceil division when downsampling so non-divisible source dimensions do not lose the final row or column.

The blur path uses a bounded working bitmap pool for downsampling scratch buffers, reducing transient bitmap allocation during repeated misses without retaining an unbounded number of bitmaps.

## Compose performance

`NeuInsets` is marked `@Immutable` so Compose can reason about its stability instead of treating every equivalent instance as an unknown mutable object.

The renderer intentionally keeps the public modifier APIs stable while the expensive bitmap generation remains behind the internal cache/blur boundary.

## Test coverage

The CI matrix contains:

- JVM unit tests for performance configuration and shadow-cache key identity.
- Instrumented Android tests for shared `BlurMaker` lifecycle.
- Concurrent blur stress coverage.
- Cache recycle/eviction/clear coverage.
- Compose UI interaction and semantics tests for switches, checkboxes, radio buttons, and sliders.
- A lightweight on-device blur timing smoke test.
- A dedicated AndroidX Macrobenchmark module for startup and frame timing.
- An AndroidX Baseline Profile generator for the demo app's startup and scrolling critical user journey.

## Macrobenchmark

The `macrobenchmark` module targets the demo application and measures:

- cold startup with `StartupTimingMetric`
- cold startup plus first-frame timing with `FrameTimingMetric`

The benchmark target uses the production-like `benchmark` build type and is marked profileable for diagnostic trace access.

Run locally on a connected Android 14+ device with:

```bash
./gradlew :macrobenchmark:connectedBenchmarkAndroidTest
```

The CI job is a smoke test for benchmark wiring and regressions. Do not treat emulator timings as representative device performance. For meaningful before/after latency and frame metrics, run the benchmark on a physical device under controlled conditions.

## Baseline Profiles

The project now contains a dedicated `:baseline-profile` test module using the AndroidX Baseline Profile Gradle plugin. The app consumes the generated rules through the `baselineProfile(project(':baseline-profile'))` dependency.

The generator exercises startup and repeated vertical scrolling so the captured profile includes both first-render work and the repeated shadow/cache paths that matter for a component-heavy Compose screen.

For the library itself, future publishing work should generate a filtered library-only profile from a representative host app so the AAR contains method-level hot rules based on observed execution rather than only hand-authored class-level hints.

## Future renderer direction

RenderScript remains the legacy API < 31 fallback. The renderer boundary is intentionally kept small so a future GPU/RenderEffect/AGSL backend can replace the old path without changing the public Compose/View APIs.

The large architectural change of making every Compose shadow generation asynchronous off the draw path is intentionally isolated from the compatibility release. Doing that safely requires moving the renderer from the legacy `DrawModifier` model to an invalidatable node/state pipeline so background completion can invalidate the correct draw node without frame-order changes.

The next renderer milestone should specifically target:

1. geometry-mask caching separate from shadow-color caching
2. adaptive quality/downsampling based on frame budget and device class
3. quantized animation-key caching for pressed/hovered elevation transitions
4. dirty-region invalidation instead of whole-shadow regeneration
5. a non-RenderScript blur backend on pre-31 devices
6. physical-device macrobenchmarks at 60/90/120 Hz with thermal-state logging
