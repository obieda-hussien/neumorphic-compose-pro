# 4.0.1 Performance & Reliability Hardening

## Renderer architecture

The renderer has a small backend boundary so Compose and View adapters can share blur behavior without exposing API-level implementation details.

On Android 12/API 31 and newer the default backend is StackBlur. On older Android versions the implementation may use the legacy RenderScript backend, with automatic StackBlur recovery when RenderScript creation or execution fails.

The RenderScript path keeps a small access-order cache of Allocation pairs per bitmap size and destroys cached resources when the backend is reset or released.

## Adaptive blur work budgeting

The expensive part of a shadow is the blur. A practical work proxy is:

    work ~= width * height * radius / sampling^3

Downsampling reduces the processed area approximately by `1 / sampling^2` and also reduces the effective blur radius approximately by `1 / sampling`.

`NeuRenderPolicy` now uses a small discrete cost model. It evaluates automatic sampling candidates and includes both the downsampled blur work and a small allowance for scaling the result back to output size.

Applications still control the minimum requested sampling through `NeuPerformanceConfig.blurDownsampling`.

The automatic selector may increase sampling up to 4, but it never reduces an explicitly requested sampling value. Explicit caller settings therefore remain a floor rather than being silently overridden.

## Allocation reduction

Internal StackBlur calls now use a disposable scratch bitmap in place. The renderer avoids the extra full-size `Bitmap.copy()` that the public `Bitmap.stackBlur()` behavior retains for callers that expect a new bitmap.

`StackBlurWorkspace` stores reusable pixel/color arrays in a bounded `ThreadLocal`. This reduces repeated array allocation for warm cache misses while dropping giant one-off workspaces instead of retaining them forever on a worker thread.

## Animation cache reuse

Spring and expressive animations produce many floating-point elevation values. Using every value as a cache key would create a new shadow bitmap for nearly every animation frame.

The renderer therefore quantizes only the expensive shadow-generation inputs to 0.5dp steps. Compose state and animation remain continuous, while nearby frames reuse the same shadow bitmap.

## Geometry-mask reuse

Background light and dark shadows share identical geometry. The renderer now caches one blurred alpha/geometry mask and applies the light and dark colors at draw time using Compose tinting.

This means a theme/color update does not require two new blur operations for the same shape geometry.

## Thermal-aware quality control

On Android 10/API 29 and newer, the shared blur holder registers a lightweight thermal-status listener. When Android reports increasing thermal pressure, the effective blur work budget is reduced in coarse steps. As the device cools, the normal budget becomes effective again.

Thermal state is part of the shadow-cache identity, so a thermally degraded render is not reused as a normal-quality render. Previously generated high-quality entries may become reusable again after cooling if they remain in the bounded cache.

Android documents the thermal status listener as the mechanism for reacting to changing device thermal pressure and reducing ongoing workload.

## Memory pressure

`NeuShadowCache` uses an LRU measured in bitmap kilobytes and responds to `ComponentCallbacks2` pressure notifications. Severe pressure clears the cache; lower pressure reduces the active budget.

The normal configured budget is not silently restored by every `NeuBlurMakerHolder.get()` call. Applications can explicitly change `NeuPerformanceConfig.shadowCacheBudgetKB` when desired.

## Testing and benchmarks

JVM tests cover performance-configuration validation, cache-key identity, and the deterministic adaptive render policy.

Instrumented tests cover shared blur lifecycle, concurrent use, cache cleanup, and warm blur timing.

Macrobenchmark now measures:

- cold startup
- startup/first-frame rendering
- component-heavy scrolling

The macrobenchmark uses `CompilationMode.Partial` with `BaselineProfileMode.Require`, so the benchmark explicitly validates the profile-guided configuration rather than silently falling back to a different compilation state.

For meaningful before/after comparisons, collect results on a physical device. Android recommends Macrobenchmark for startup and runtime rendering measurements, and `FrameTimingMetric` exposes `frameOverrunMs` as a useful modern jank signal where available.

## Next renderer milestone

The next major architectural step should migrate the legacy `DrawModifier` implementation to a `Modifier.Node`/`DrawModifierNode` renderer. Current Compose APIs expose node lifecycle hooks, a node-owned `coroutineScope`, and `invalidateDraw()`, making them a stronger foundation for asynchronous shadow generation.

Official reference:
https://developer.android.com/reference/kotlin/androidx/compose/ui/node/DrawModifierNode
https://developer.android.com/reference/kotlin/androidx/compose/ui/Modifier.Node

The next milestone should introduce:

1. geometry generation separate from color composition for foreground shadows
2. asynchronous shadow generation with request-version checks so obsolete renders are dropped
3. a two-level hot/protected shadow cache or TinyLFU-style admission
4. frame-budget-aware quality changes with hysteresis
5. physical-device benchmarks at 60/90/120 Hz and thermal-state capture
6. a modern non-RenderScript backend for pre-31 devices

The mask-first path uses Compose image tinting so expensive geometry can stay cached while colors change. Official reference:
https://developer.android.com/develop/ui/compose/graphics/images/customize

The architectural goal is simple: expensive work happens off the critical draw path, completed results are atomically swapped into the node, and the node invalidates only the required drawing layer.
